# Portal Platform Target Architecture

Version 2 (after review) · November 2026

The portal is the single front door: self-service, catalog, scorecards and workflow status. Behind it, Azure DevOps holds the intent and the platform code, Argo CD syncs it into a management cluster, Crossplane reconciles the real resources, Gatekeeper (OPA) governs the cluster and OpenTelemetry reports what happened.

Version 2 adds the safety rails (deterministic names, prune protection, pause, commit serializer), a preview step, an action runner for one-shot operations, platform metrics and generated providers.

## 1. Principles

- **Intent, not scripts.** A developer states what should exist. The spec contains no step order, no API calls and no IDs.
- **Git is the source of desired state.** Every change is a commit; history is the audit log.
- **Reconcilers do the work, continuously.** A failure or a manual change is corrected on the next pass, not by a rollback script.
- **The portal writes one thing and reads three.** It commits specs (and triggers one-shot workflows). It reads the tools, the cluster and the telemetry backend.
- **Observed state wins.** The catalog is filled from what exists, never from a workflow claiming it succeeded.
- **One identifier everywhere.** `team/service` names the entity in every feed; a run ID follows one request through every hop.

## 2. System overview

### 2.1 Zones

| Zone | Contents |
|---|---|
| Portal (your platform) | Self-service, pre-check + preview, catalog + scorecards, workflow status, ingestion |
| Azure DevOps + ACR | Portal repo, Crossplane project, two CI pipelines, Azure Container Registry |
| Management cluster (AKS) | Argo CD, Crossplane + providers, Gatekeeper, OTel Collector, catalog watcher, External Secrets Operator, action runner (Argo Workflows) |
| Platform tools | Azure DevOps, SonarQube, Vault, Entra ID, Azure |
| Observability backend | Loki (logs, events), Tempo (traces), Prometheus (metrics) |

### 2.2 Flows

Intent (desired state), flowing down:

```
Developer
  └─ submits form ─▶ Portal
        ├─ pre-check: render + OPA + preview
        ├─ upserts entity (status Requested, run_id)
        └─ commits spec to Portal repo, branch main (services/<team>/<service>.yaml)
              └─ webhook ─▶ Argo CD (management cluster)
                    └─ applies Service XR ─▶ Gatekeeper admission
                          └─ Crossplane Composition renders managed resources
                                └─ Providers create / update / fix drift in
                                   Azure DevOps · SonarQube · Vault · Entra ID · Azure
```

One-shot operations (imperative), flowing down:

```
Portal action ("should happen once") ─▶ Argo Workflows template (actions/) ─▶ tool APIs
```

Observed state, flowing back:

```
Tools ──(API sync / webhooks)──────────────────▶ Portal ingestion
Cluster: XR + MR status, Gatekeeper violations ─▶ catalog watcher ─▶ Portal ingestion
Argo CD, Crossplane, providers ──(logs, events, spans, metrics)──▶ OTel Collector ─▶ Loki / Tempo / Prometheus
Portal workflow status ──(query by run_id)────▶ Loki / Tempo
```

Platform delivery:

```
Portal repo CI ── validates, packages ──▶ ACR (Configuration package)
Crossplane project CI ── tests, builds, signs ──▶ ACR (provider images)
Argo CD applies the repo; Crossplane installs pinned packages from ACR
```

## 3. Components

| Component | Role | Writes to | Reads from |
|---|---|---|---|
| Portal | Self-service, approvals, pre-check + preview, catalog, scorecards, workflow status | Portal repo (`services/`), Argo Workflows (one-shot) | Tools' APIs, cluster API (via watcher), Loki/Tempo/Prometheus |
| Portal repo (ADO) | Intent + platform definition: specs, XRDs, Compositions, policies, Argo CD apps, workflow templates | ACR (via CI) | — |
| Crossplane project (ADO) | Source of custom/generated providers; one repo per provider | ACR (provider images) | — |
| Argo CD | Keeps the cluster equal to `main`; `Prune=false` on team apps; custom health checks for Crossplane kinds | Cluster API | Portal repo |
| Crossplane + providers | Turns Service XRs into real resources; corrects drift. Providers: upstream first, Upjet-generated second, hand-written last | Tools' APIs | Cluster API, ACR |
| Gatekeeper (OPA) | Admission on every XR and managed resource; audit every 60 s | Constraint status | Constraints synced by Argo CD |
| OTel Collector | Collects logs, events, spans, metrics; tags with `run_id` and `service` | Loki, Tempo, Prometheus | Pod logs, k8s events, OTLP |
| Catalog watcher | Your agent on the cluster; mirrors XR/MR status and violations into entities | Portal ingest API | Cluster API (watch) |
| External Secrets Operator | Delivers provider credentials from Vault into the cluster | Kubernetes Secrets | Vault |
| Action runner (Argo Workflows) | Runs one-shot operations triggered by the portal; same run ID and telemetry | Tools' APIs | WorkflowTemplates from the Portal repo |

### 3.1 Cluster layout

- Namespaces: `argocd`, `crossplane-system`, `gatekeeper-system`, `otel`, `portal-agent`, `external-secrets`, `argo-workflows`.
- One namespace per team for its Service XRs (Crossplane v2 model: XRs are namespaced). RBAC and quotas map to teams; the watcher derives the owner from the namespace.
- Provider credentials: Vault → External Secrets → `ProviderConfig`. One Vault role per provider, least privilege.
- Private AKS, outbound only; egress allow-list to the tools' endpoints.

### 3.2 Portal ↔ cluster access

- **Read:** the catalog watcher runs in the cluster with a ServiceAccount allowed to `watch` XRs, managed resources and Constraints. The portal never holds a kubeconfig.
- **Write:** the portal writes only to Git (and submits Argo Workflows through a dedicated, scoped identity). Argo CD is the sole writer of XRs; Gatekeeper enforces this.
- **Policy "write" by the portal** means committing a new Constraint to `policies/constraints/`. Argo CD applies it; nothing is applied directly.

## 4. The two Azure DevOps projects

The Portal repo defines *what the platform offers and what teams asked for*. The Crossplane project holds *code that teaches Crossplane how to talk to tools without a good provider*. They have different change rates and different reviewers.

### 4.1 ADO project "Portal" · repo `portal-platform`

```
portal-platform/
├─ services/                  # intent, written by the portal
│  └─ team-payments/
│     ├─ team.yaml
│     └─ payments-api.yaml
├─ platform/
│  ├─ xrds/                   # Service API (OpenAPI schema)
│  │  └─ service.yaml
│  ├─ compositions/           # golden paths, one revision each
│  │  ├─ java-api-v3.yaml
│  │  └─ frontend-v1.yaml
│  ├─ functions/              # composition functions (KCL / Go)
│  ├─ tests/                  # crossplane render + assertions
│  └─ crossplane.yaml         # Configuration package manifest
├─ actions/                   # Argo WorkflowTemplates (one-shot ops)
├─ policies/
│  ├─ rego/                   # shared Rego: portal + CI + cluster
│  ├─ templates/              # Gatekeeper ConstraintTemplates
│  └─ constraints/            # Gatekeeper Constraints
├─ argocd/
│  ├─ applicationset.yaml     # one app per team folder
│  └─ platform-app.yaml       # XRDs, compositions, policies, actions
└─ azure-pipelines.yml        # CI: build + validate
```

CI (build + validate): `kubeconform` on specs, `crossplane render` + assertions on compositions, `conftest` with the shared Rego, `gator test` on constraint templates, then `crossplane xpkg build` and push of the Configuration package to ACR.

Branch policies: humans need PRs everywhere. The portal identity has "bypass policies when pushing" limited by a path filter to `services/**`. `platform/**`, `policies/**` and `actions/**` always go through PRs with CODEOWNERS (platform team, security for policies).

### 4.2 ADO project "Crossplane" · one repo per provider

```
provider-sonarqube/
├─ apis/                      # CRDs: Project, QualityGate, Webhook
├─ internal/controller/       # observe · create · update · delete
├─ internal/clients/          # SonarQube REST client
├─ package/crossplane.yaml    # Provider package manifest
├─ examples/
└─ azure-pipelines.yml        # CI: provider images

provider-ado-extras/          # branch policies, service hooks, anything the upstream provider lacks
```

Provider strategy:

1. Use upstream providers (Azure, Entra ID/azuread, Azure DevOps) where they cover the need.
2. Generate with **Upjet** from an existing Terraform provider (`azuredevops` and `sonarqube` both exist). This gives Observe/Create/Update/Delete for free.
3. Hand-write with crossplane-runtime (Go) only what no Terraform provider covers.
4. Fallback for the long tail: `provider-terraform` (OpenTofu) or a Composition function calling Terraform.

CI (provider images): `go test`, build, `cosign` sign, `crossplane xpkg push` to ACR.

The repo's `Configuration` and `Provider` manifests pin ACR tags. Bumping a tag in Git is how a new golden-path version or provider build reaches the cluster; every change is in history and can be reverted by Argo CD.

## 5. The intent: one file per service

The spec says *what*, never *how*. The golden-path version is a field, which is how existing services are upgraded later: one value changed in one file.

```yaml
apiVersion: platform.acme.io/v1alpha1
kind: Service
metadata:
  name: payments-api
  namespace: team-payments
  annotations:
    portal.acme.io/run-id: r-8f2c
spec:
  owner: team-payments
  goldenPath:
    name: java-api
    version: "3"            # selects the Composition revision
  compositionUpdatePolicy: Manual
  repository:
    template: java-spring-api
  quality:
    sonarqube: true
    qualityGate: acme-default
  secrets:
    vault: true
  environments: [dev, staging, prod]
  costCenter: CC-4711
```

### 5.1 One schema, three consumers

The XRD (CompositeResourceDefinition) holds an OpenAPI v3 schema for `Service`. The same schema:

- generates the portal form (fields, enums, defaults);
- validates PRs in CI (`kubeconform`);
- is enforced by the cluster API on admission.

A field added to the schema shows up everywhere at once. Without this, the form and the backend drift apart.

### 5.2 Schema and composition evolution

- XRD versions with conversion (`v1alpha1 → v1beta1`); deprecated fields kept for two releases.
- Each XR sets `compositionUpdatePolicy: Manual`. The portal offers "upgrade to v4" per service or per team batch; a Composition change never rolls out to every service at once.
- CI runs `crossplane render` with assertions, and provisions an ephemeral test service on every platform PR.

## 6. One request, end to end

A **run ID** is created by the portal when the form is submitted. It travels through the commit, the XR, every managed resource and every log line.

Synchronous (seconds):

1. Developer submits the form.
2. Portal renders the Composition (`crossplane render`), evaluates the shared Rego and shows a **preview**: the list of resources that will be created and the policy result. The user confirms. Approval, if required, happens in the portal.
3. Portal upserts the catalog entity: lifecycle `Requested`, `lastRunId = r-8f2c`, owner, golden path, relations.
4. Portal commits `services/<team>/<service>.yaml` to `main` through its commit queue (rebase and retry on a push race). Commit trailers: `Run-Id: r-8f2c`, `On-Behalf-Of: <user>`.

Asynchronous (minutes):

5. ADO webhook triggers an Argo CD sync of the team's application.
6. Argo CD applies the Service XR. Gatekeeper admission evaluates it.
   - 6b. If denied: the sync fails, the app is OutOfSync with the denial message, the watcher forwards it to the run. This is the only way a bad spec gets past the pre-check (manual PR, kubectl).
7. Admitted: Crossplane selects the Composition revision and renders managed resources, each labelled `portal.acme.io/run-id` and `portal.acme.io/service`.
8. Providers create or update resources in the tools. Dependencies are references, not a step list: the pipeline resource waits until the repo reports its ID.
9. Providers emit logs and spans tagged with the run ID; the OTel Collector ships them to Loki/Tempo.
10. The catalog watcher reports XR conditions (`Ready`, `Synced`, `Degraded` with message) to the portal.
11. The portal's workflow page queries Loki/Tempo by `run_id` and renders a step timeline.
12. Tool integrations sync observed properties: repo URL, pipeline ID, Sonar key, quality gate, RBAC groups.
13. Entity lifecycle becomes `Ready`.

### 6.1 Run ID propagation

| Hop | Where the run ID lives | Who sets it |
|---|---|---|
| Portal | Run record, entity property `lastRunId` | Portal |
| Commit | Trailer `Run-Id`, spec annotation `portal.acme.io/run-id` | Portal |
| Service XR | Annotation, synced as-is | Argo CD |
| Managed resources | Labels `portal.acme.io/run-id`, `portal.acme.io/service`, copied by the Composition | Composition function |
| Provider logs / spans | Structured field `run_id` read from MR labels | Custom/generated providers directly; upstream providers via the collector (MR name → labels) |
| Loki / Tempo / Prometheus | Index label `run_id` | OTel Collector |

### 6.2 Lifecycle states

```
Requested ─▶ Committed ─▶ Synced ─▶ Reconciling ─▶ Ready ─▶ Deleting
                │                        │  ▲            │
                ▼                        ▼  │            │
             Rejected                 Degraded ──────────┘
          (pre-check or               (auto-retry)   drift or spec change
           admission denied)                         returns Ready to Reconciling
```

`Ready` is not an end state. A manual deletion of a resource or a golden-path version bump sends the service back to `Reconciling`, and it returns to `Ready` by itself.

## 7. What the portal ingests

Yes, the portal ingests Crossplane resources: they are the only source for "managed by platform", health and golden-path version. They are not the only feed.

| Feed | Source | Mechanism | Owns these properties |
|---|---|---|---|
| 1. Tool integrations | ADO, SonarQube, Azure, Entra ID | Webhooks first, polling as backstop | `repoUrl`, `pipelineId`, `sonarKey`, `qualityGate`, `rbacGroups` |
| 2. Catalog watcher | Service XRs, managed resources | Kubernetes watch | `xrReady`, `xrSynced`, `managedBy`, `goldenPathVersion`, conditions, run ID |
| 3. Gatekeeper audit | `Constraint.status.violations` | Kubernetes watch (same watcher) | `violations[]` per service and policy |
| 4. Loki / Tempo | Logs, events, traces | Queried on demand by `run_id`, not stored | Run timeline (cached once terminal) |

Entity model:

- **Identifier:** `team/service`, computed identically by the portal and every feed, so they update one entity and never create duplicates.
- **Intent properties (portal owns):** owner, goldenPath, costCenter, requestedBy, lastRunId, relations (team, environments), lifecycle.
- **Observed properties (feeds own):** everything in the table above. No feed writes another's properties.
- **Derived (scorecards):** Managed by platform · On current golden path · Quality gate passes · No policy violations · Has owner and on-call · Secrets from Vault.
- **Legacy services** appear from feed 1 only, with `managedBy: legacy`.

## 8. Governance with OPA

One set of Rego policies in `policies/rego/`, enforced at three points:

| Point | Where | Input | Effect |
|---|---|---|---|
| 1. Portal, before commit | OPA as library or sidecar | Rendered Service spec (and rendered resources) | Error shown in the form; nothing is committed |
| 2. CI, every change | `conftest` on specs and compositions, `gator test` on templates | Files in the PR | Blocks merge of manual PRs |
| 3. Gatekeeper, cluster | Admission on XR, MR, Compositions; audit every 60 s | AdmissionReview | Hard guarantee; violations flow back to the catalog |

Notes:

- Gatekeeper evaluates an AdmissionReview; the portal evaluates a raw spec. Keep rules in plain Rego packages with a thin input adapter per entry point, and pin the same OPA version.
- Audit violations → catalog watcher → `entity.violations[]` → "No policy violations" scorecard.
- Example policies: prod requires an on-call group; every service sets a cost centre; only approved Composition revisions may be referenced; managed resources must carry `portal.acme.io/service`; nobody but Argo CD may create XRs in team namespaces; DELETE on XRs labelled `protected=true` requires an approved decommission run ID.

## 9. Observability with OpenTelemetry

Sources and signals:

| Source | Signal | Receiver |
|---|---|---|
| Argo CD | Sync events, application status | `k8s_events` |
| Crossplane core | XR events, conditions | `k8s_events` |
| Upstream providers | JSON logs on stdout | `filelog` |
| Custom / Upjet providers | OTLP spans and logs with `run_id`; `/metrics` | `otlp`, `prometheus` |
| Action runner | OTLP spans per workflow step | `otlp` |

Collector (DaemonSet): receivers `otlp`, `filelog`, `k8s_events`, `prometheus`; processors `k8sattributes` (pod labels), `transform` (managed-resource name → `run_id`, `service`), `batch`; exporters `loki`, `otlp/tempo`, `prometheusremotewrite`. Labels on every record: `run_id`, `service`, `step`, `provider`.

Honest limits:

- Upstream providers emit no spans. The run timeline is built from Kubernetes events and XR conditions first, logs second. Real distributed traces exist only for custom/generated providers and the action runner.
- The portal keeps no copy of logs. It queries on demand when a run page is opened, and caches the timeline on the run record once the run is terminal.

Platform SLOs in Prometheus: time-to-Ready per golden path, reconcile error rate per provider, ADO API rate-limit hits, Argo sync duration, Gatekeeper denials per policy.

Example run page for `r-8f2c`:

```
09:41:02  Committed
09:41:20  Synced (Argo CD)
09:41:48  ADO project        ✓
09:42:10  Repository         ✓
09:42:31  SonarQube project  ✗  "quality gate 'acme-default' not found"  → retrying
```

## 10. Safety rails

### 10.1 Deterministic external names

Crossplane's link to a real resource is the `external-name` annotation, which is cluster state, not Git. Without this rule, losing the cluster would make Crossplane recreate everything.

- Every Composition derives names from the spec: ADO project `{team}-{service}`, Sonar key the same, resource groups `rg-{service}-{env}`.
- A rebuild from Git then becomes an adoption, not a duplication.
- Phase-1 milestone: delete the cluster, rebuild from Git, confirm zero new resources.

### 10.2 Prune and delete protection

- Team Argo CD apps run with `Prune=false`; deletion is an explicit decommission action.
- Gatekeeper blocks DELETE on XRs labelled `protected=true` unless the request carries an approved decommission run ID.
- `deletionPolicy: Orphan` on repos, projects and anything holding data.
- Argo CD custom health checks (Lua) for Crossplane kinds, so `Ready` and `Degraded` display correctly instead of "Progressing" forever.

### 10.3 Pause and break-glass

- Annotation `portal.acme.io/paused: "<expiry>"` on the XR; the Composition switches every managed resource to `managementPolicies: [Observe]`.
- Set from the portal with a reason; shown on the entity; auto-expires.
- Manual changes made while paused appear as drift when it ends; the portal asks: keep (update the spec) or revert.

### 10.4 Commit serializer and scoped bypass

- One commit queue in the portal: rebase and retry on non-fast-forward pushes.
- Branch policy path filter: bypass applies to `services/**` only.
- Commit trailers `Run-Id` and `On-Behalf-Of` for audit.
- The portal identity is the most powerful credential in the platform: hardware-backed secret or workload identity, rotated, alerted on use outside the portal.

### 10.5 Decommission and credential handoff

- Decommission is a portal action with approval: choose archive vs delete per resource; the spec is then removed and the XR enters `Deleting`, reporting what was actually removed.
- New pipelines authenticate with workload identity federation (Entra) instead of stored SP secrets; the Composition creates the federated credential and the ADO service connection.
- Cost centre from the spec is propagated as a tag on every Azure resource and ADO project.

## 11. One-shot operations

Not everything is a desired state. Restart, rotate a secret, re-run a scan, grant temporary access: these should happen once and leave the spec untouched.

- The portal decides per action which verb applies: "should exist" → commit a spec; "should happen" → submit an Argo Workflow.
- WorkflowTemplates live in `actions/` in the Portal repo and are synced by Argo CD like everything else.
- Both paths carry the run ID, so the developer sees the same timeline and the audit log reads the same.
- Workflows are idempotent and use the same provider credentials through External Secrets.

Rule of thumb: if the user asks for something to exist, use a spec and a reconciler. If they ask for something to happen once, use a workflow. Mature platforms use both.

## 12. Scale and resilience

- **Repo split threshold.** One repo is right to start. Split into `platform-definition` (XRDs, compositions, policies, actions) and `platform-intents` (specs) when you pass roughly 200 services or CI on `main` exceeds two minutes. Argo CD apps per team folder keep refresh cost bounded until then.
- **Management cluster availability.** Services keep running without it, but no change can be made. Target: a second cluster bootstrapped from the same Git (active/standby) or a tested rebuild runbook under one hour. Deterministic names make either possible.
- **Event-driven ingestion.** ADO and SonarQube webhooks feed the integrations; polling is only a backstop, so the catalog does not lag the workflow page.
- **Crossplane v2 model.** XRs are namespaced and claims optional. Team namespaces hold their Service XRs directly.
- **Provider rate limits.** Set provider poll intervals deliberately; watch ADO API rate-limit metrics; use webhooks for Argo rather than polling.

## 13. Legacy resources

Ingest everything now, import selectively later.

1. **Ingest (day one).** Integrations give full visibility with no risk. Every entity gets `managedBy: crossplane | legacy`. Scorecard rule "Managed by platform" makes the migration visible.
2. **Adopt on touch.** Import a service when a team asks for a change on it, a compliance requirement applies, a golden-path migration is planned, or it is critical and actively developed. Leave as legacy: anything soon to be decommissioned, one-off setups that fit no golden path, stable low-change resources.
3. **Import safely.** Set `crossplane.io/external-name` to the real ID (deterministic names make this automatic when the name already matches). Go in three steps: `managementPolicies: ["Observe"]` → compare and adjust → full management with `deletionPolicy: Orphan`. The Composition accepts an optional `spec.adopt` block with existing IDs when names differ.

| Stage | Legacy resources | New resources |
|---|---|---|
| Visibility | Ingested, `managedBy: legacy` | Ingested + Crossplane status |
| Changes | Adopt first, then spec | Spec via portal |
| Drift correction | No | Yes |

## 14. Looking ahead

- **AI agents as platform users.** Expose the catalog and every action through an API and an MCP server. Agents get their own identities with narrower rights (create in dev, propose for prod); commits and runs record `On-Behalf-Of`. Agents write intent, never call tool APIs directly.
- **Interoperability.** Keep the entity model exportable as Backstage `catalog-info.yaml` and Port blueprints.
- **Spec standards.** Compare the Service XRD with Score (workloads) and Kratix promises before freezing it.
- **Application delivery.** Decide whether the Service spec also declares environments and a deploy pipeline, and where workload clusters' GitOps lives (separate Argo CD per workload cluster, fed by app repos). Otherwise teams will build it themselves, inconsistently.
- **Lean path if the team is small.** OpenTofu modules run from ADO pipelines on commit, nightly plan-and-alert for drift, same portal, repo layout, run ID, OPA and telemetry. Crossplane then replaces pipelines one resource type at a time. The spec and the catalog feeds are identical on both paths.

## 15. Decisions recorded

| Decision | Choice | Why |
|---|---|---|
| Where specs live | Portal repo, `services/<team>/` | One repo, one ApplicationSet; CODEOWNERS per team folder for manual PRs |
| How the portal writes | Direct commit to `main` after pre-check and approval | No PR to resolve outside the portal |
| Unit build | CI that validates and packages the platform | Old pipeline units are retired as providers cover their tools |
| Custom providers | Separate ADO project | Different reviewers and release cadence |
| Provider strategy | Upstream first, Upjet-generated second, hand-written last | Hand-written providers are the most expensive, least reusable part |
| Telemetry path | Collector → Loki/Tempo/Prometheus; portal queries | Portal stays stateless for logs; backend handles retention |
| OPA scope | Admission + audit in cluster, same Rego in portal and CI | Fast feedback in the form, hard guarantee in the cluster, one source of rules |
| Crossplane ingestion | Yes, via a catalog watcher | Only source for managed/health/version |
| Legacy resources | Ingested as `managedBy: legacy`; adopted on touch | Visibility day one, risk spread over time |
| External names | Deterministic from the spec | Cluster rebuild becomes adoption |
| Deletion | `Prune=false`; explicit decommission; Orphan on data | A removed file can never delete a repo by accident |
| Portal commits | Serialized queue; bypass scoped to `services/**` | No push races; platform code always reviewed |
| One-shot operations | Argo Workflows templates in `actions/`, same run ID | Imperative logic out of specs without a second UX |
| Composition updates | Manual per XR, batch upgrade from the portal | Platform changes roll out deliberately |
| Metrics | Prometheus via the collector; SLOs on time-to-Ready and provider errors | Logs show one run; metrics show the platform degrading |

## 16. Open questions

- Loki/Tempo/Prometheus self-hosted vs Azure Monitor (Log Analytics + Application Insights + managed Prometheus). Same design; only the portal's query layer changes.
- Whether upstream ADO provider coverage is enough or `provider-ado-extras` is needed from day one. Check branch policies and service hooks first.
- Run retention: how long the portal keeps cached run timelines after the backend's log retention expires.
- Gatekeeper vs Kyverno in the cluster. Kyverno is easier to author; Gatekeeper shares Rego with the portal pre-check.
- Active/standby management cluster vs a rebuild runbook. Decide after the phase-1 rebuild drill shows the real recovery time.
- Application delivery scope (see 14).

## 17. Build order

| Phase | Scope | Milestone |
|---|---|---|
| 1. Backbone | AKS, Argo CD, Crossplane with upstream Azure/Entra/ADO providers, Portal repo with XRD + one Composition (java-api), CI validates and packages | A service is rebuilt from its spec alone; a cluster-delete drill produces zero duplicate resources |
| 2. Governance + safety rails | Gatekeeper with first constraints, External Secrets from Vault, Rego shared with CI, `Prune=false`, delete protection, pause annotation | A non-compliant spec is refused in CI and in the cluster; deleting a file deletes nothing |
| 3. Observability | OTel Collector, Loki/Tempo/Prometheus, run-ID propagation through the Composition, first SLO dashboard | A run can be followed end to end by its ID; time-to-Ready graphed per golden path |
| 4. Portal read side | Tool integrations, catalog watcher, scorecards, workflow status page | Every existing service visible with `managedBy` |
| 5. Portal write side | Self-service form generated from the XRD, render + OPA preview, approvals, serialized commit, first Argo Workflows actions | Tickets closed; developers create services and run day-2 actions themselves |
| 6. Generated providers + adoption | Upjet provider-sonarqube, then ado-extras; adopt legacy on touch; composition batch upgrades | The last old pipeline unit is retired |

Sizing: this is roughly a 12-month programme for three to five engineers who know Kubernetes, Crossplane and Go. With a smaller or newer team, start on the lean path (section 14) and keep this document as the target.

## 18. Glossary

- **XRD** — CompositeResourceDefinition: the schema of a Crossplane API such as `Service`.
- **XR** — Composite resource: one instance of that API (one service).
- **Composition** — the golden path: a template that expands an XR into managed resources; versioned by revision.
- **MR** — Managed resource: one real thing in a tool (an ADO project, a Sonar project), owned by a provider.
- **Provider** — Crossplane controller that knows one tool's API. Upjet generates providers from Terraform providers.
- **External name** — the real ID Crossplane uses to find a resource in the tool.
- **Management policies** — per-MR verbs Crossplane may use (`Observe` only, or full `*`).
- **Gatekeeper** — OPA admission controller and auditor for Kubernetes.
- **Catalog watcher** — your agent that mirrors cluster state into portal entities (equivalent of Port's Kubernetes exporter).
- **Run ID** — identifier created by the portal per request, carried through every hop for status and audit.
- **Golden path** — an opinionated, supported way to create a kind of service; here, one Composition revision.

Names such as `platform.acme.io`, `portal.acme.io` and `r-8f2c` are placeholders.
